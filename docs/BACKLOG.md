## 2026-10-30 · interop-matrix 增加传输层列

**要做什么**：在互操作矩阵中增加传输层指标列——QUIC/TLS 握手时延、ClientHello 体积、协商到的
组与签名算法、服务端实现指纹。

**为什么有价值**：论文与客户材料都需要"迁移后的端到端代价"，目前矩阵只覆盖 KEM 的字节一致性，
不含传输层。

**为什么现在不做**：加列意味着重跑矩阵、重新封存记录（新摘要清单 + 新 RFC 3161 令牌），属于
解冻工程线并产出新证据，与当前"论文只做文档、工程线冻结"的决策冲突。

**替代方案（已采用）**：论文与白皮书直接引用 PQ Crypta 的 QUIC 实测数据，并随数据引用其免责
声明（测量客户端栈为 `quinn` / `h3`，非受控基准，不覆盖浏览器栈）。我们不重跑、不改写其数字。

**解冻条件**（任一）：
1. 出现第二个消费方（客户交付明确要求自有传输层数据，或论文返修被要求补自有测量）；
2. 需要出具 L3 级传输层证据（时间戳封存），而第三方数据无法满足引用要求。

**解冻时的最小动作**：先补一列、只跑一组种子、单独封存，不重写既有 `lg-116` 记录。

## 2026-10-30 · Verifact 批量对账（产物绑定）

**要做什么**：把 `verifact` 的「声明 → 产物」绑定从少量样本扩到全量交付物：每条声明产出可复算的
绑定记录（claim id → 文件 → sha256 → 复核命令），并显式输出未绑定清单。

**为什么有价值**：尽调时「你说你测过」与「这条声明能一键复算」是两个信任层级。未绑定数目前是外部
最容易被挑的点。

**为什么现在不做**：全量绑定要重跑取证链并重新封存（新摘要清单 + 新 RFC 3161 令牌），属解冻工程线；
且 claim 粒度需按客户口径定，先做等于先猜。

**解冻条件**（任一）：① 拿到第一个 B 端 POC 且对方明确要求逐条底稿；② 论文返修要求提供完整
claim ↔ 产物对照。

**预估工作量**（未开工，仅量级）：绑定策略定稿 0.5 天 + 脚本化 2–3 天 + 全量重跑与封存 1–2 天。

**触发场景**：客户尽调清单里出现 evidence mapping / traceability matrix 一类要求。

**解冻时的最小动作**：只对交付层 14 件摘要清单做到 100% 绑定，不动研究线。

## 2026-10-30 · Tauri 补 Linux / macOS

**要做什么**：`fibemate-tauri` 在三平台出包，并跑同一套冒烟。

**为什么有价值**：客户环境异构，「只有 Windows 包」在采购评审里是硬伤。

**为什么现在不做**：纯适配体力活，无技术壁垒。当前定位是工程验证台，Windows 可用即满足证据需要。

**解冻条件**：出现第一个使用 macOS / Linux 的企业客户，或发布渠道要求多平台安装包。

**预估工作量**（未开工，仅量级）：macOS 1–2 天（含签名与公证链）、Linux 2–3 天（含 WebKitGTK 版本
矩阵）、CI 0.5–1 天。

**触发场景**：客户说「我们公司用 Mac」。

**解冻时的最小动作**：先出 macOS 未签名冒烟包，不做公证。
