## 0. 三条规定

1. **没有量化就写 unquantified。** 任何形容词（「稳健」「安全」「已加固」）都不能替代一次测量。
2. **只声明覆盖的故障模型，不写 fault proof。** 结论的正确形式是「在这组注入故障下没有释放错误签名」，不是「抗故障」。
3. **引用逐条回源。** 标题、作者、venue、年份从 ePrint 或出版方页面抄，参考文献表记录核对日期；核不到的引用直接删，不软化。

## 1. 本文是什么、不是什么

**是**：一个 Falcon 签名路径的**范围界定与取证计划**，写在任何移植落地之前，目的是让评估标准先于实现存在——否则实现会悄悄定义标准。

**不是**：安全证明、新的密码分析、对任何第三方库的审计、「恒定时间」声明、FIPS 206 合规声明。

## 2. 标准状态（核对日期 2026-11-19，需在发布前重核）

### 3.2 这些事实支持与不支持什么

- **支持**：本项目目前没有任何自研 Falcon 代码，因此不存在「我们的实现已通过 X」这类陈述的成立条件；任何关于 Falcon 的行为描述都只能来自规格与文献。
- **支持**：`www/noble-pq/index.js` 引用的第三方实现，是这个仓库里**唯一**可达的 Falcon 代码路径。
- **不支持**：「我们支持 Falcon」。引用一个库不等于实现它，也不等于评估过它。
- **不支持**：把站点里那份第三方实现当成基线来写安全结论——它未被本项目评估过，且运行在明示非机密的浏览器环境（见 §9 第 1 条）。

### 3.3 依赖事实

- `@noble/post-quantum` 是外部依赖，随站点打包；本文只声明「它存在且被引用」，不声明其侧信道属性。
- Falcon 的采样器依赖 SHAKE-256 / RNG；这两条路径与现有 ML-KEM/ML-DSA/SLH-DSA 共享，属于 T9 的依赖面。

## 4. 资产与对手模型

**资产**：NTRU 私钥基 (f, g, F, G)；每次签名的 salt；由私钥导出的 FFT 中间值；接受/拒绝判定及其迭代次数。

| ID | 对手 | 能力 | 现实信道 |
| --- | --- | --- | --- |
| A1 | 远程 | 提交待签消息，观察墙钟时间与响应 | 网络计时，粒度粗 |
| A2 | 同机非 root | 同宿主跑代码 | 缓存（prime+probe）、缺页、调度计时 |
| A3 | 本地非特权 | 可读性能计数器（若有权限） | 分支误预测、缓存缺失、指令计数 |
| A4 | 物理接触 | 持有或借用设备 | 功耗/电磁迹，无屏蔽时可单迹 |
| A5 | 故障注入 | 时钟/电压/激光，或投毒的依赖 | FFT、采样器、范数检查处的位翻转 |
| A6 | 坏 RNG | salt 或采样字重复/可预测 | 重复或偏斜的签名 |
| A7 | 集成误用 | API 接错 | 缺 salt、跨方案复用密钥、验证工作量不限 |

**能力边界（写进本文就是承诺）**：不建模「对手能改我们的源代码仓库」；不建模「对手控制宿主的 RNG 且我们无法检测」——后者按 A6 处理，要求**失败必须响亮**（§6.4）。

### 5.2 逐条判据（关键三条展开，其余按表执行）

**T1（拒绝循环）**——最容易被「实现细节」掩盖的一条。
- 泄漏对象不是迭代次数本身，而是**迭代次数与私钥范数的相关性**。所以证据必须是分布，不是平均值。
- 判据：① 10^5 次签名的迭代次数直方图（按私钥固定 / 按密钥集随机两组）；② 循环计数上的固定 vs 随机 TVLA，报样本量与 |t|；③ 用 R6 的提示攻击成本模型把分布折算成「攻击者需要多少次签名、BKZ 块大小降到多少」。
- **泄漏界必须由独立读者签字**（§9 第 3 条）：采样器作者不得自签。
- **资源受限时的退路（不等于免签）**：确实找不到外部密码学专家时，由项目内**不负责该模块的作者**（主架构师或 CTO）独立复核并出具**书面**意见；签字人与采样器作者不得是同一人，意见里必须写明「资源受限下的替代签字」。这条只降低门槛，不取消签字本身。
- 如果折算不出数字，写 `unquantified`，并说明卡在哪一步——「unquantified」与「安全」是两句话。
- **措辞锁死**：分布与攻击成本任一项跑不出，结论只能是 `unquantified`；**不得**用「安全」「已加固」「未观察到泄漏」替代。这不是文风偏好：`unquantified` 是「没测到」，`safe` 是「测过且没有」，两者不能写在同一格里。

**T2（浮点精度与 FFT 暴露）**——两条独立的线，不要混为一谈。
- **实现暴露线**：实现在浮点上做 FFT，中间值直接由私钥派生；R1 在 Cortex-M4 上用约 10k 条差分 EM 迹恢复密钥，R2 用单条功耗迹在 `-O0/-Os/-O3` 下报告 100% 恢复（PQClean 目标）、对内嵌汇编目标 10 条迹恢复 53/100 个密钥。这两条说明的是**未受保护实现的暴露性**，不是我们的实现的结论。
- **精度线**：R7 指出标准 double（53 bit）**不满足**安全高斯采样器所需的已证误差界，三字算术（≥72 bit）满足，代价约 1.84×。
- **2026-11-19 追加（R8）**：R8 把这条缺口量成了查询预算——双精度下每个密钥可用的签名查询约 2^61.5（Falcon-512）/2^58.7（Falcon-1024），低于 2^64 目标；32.64 定点实现达 2^99.7/2^96.7。这不是「double 可被利用」的证据，而是「缺口有多大」的证据。所以 T2 的判据在②之外再加一项：**报出所选精度下的每密钥查询预算，并写明它相对目标安全级的余量**。- **2026-11-20 追加（R13，preprint）**：R13 给出 Falcon 定点 FFT 采样器的 Rényi 界——λ=128（n=512）下 plain center 保 126.28 bit、fractional center 保 126.70 bit；λ=256（n=1024）下分别保 248.78 / 253.53 bit；前提是对密钥生成接受的所有密钥成立，签名预算 2^64 次。它把「定点实现是否安全」从定性讨论变成可引用的定量对照。**但它是 preprint，不是已见刊结论**：本文只把它用作 T2 精度线的外部参数对照，不写成已证事实。该文同时自述其浮点 signer 的闭合分析遇到数值矛盾并标为 open——这种「承认没做完」的标注方式与本稿的口径一致，值得照抄。
- 判据：① FFT 路径按引用逐分支审计（列出分支与内存索引，给文件行号，是清单不是结论）；② 该路径 dudect；③ 精度需求写成已证界 + 本文档声明它需要多少位。
- **本文不声称 double 可被利用**：R7 自己写明目前没有已知的实际攻击。我们报告「界上的缺口」，不多说一个字。
- **口径固定（两侧都不许）**：文献给的是**有界差**（已证误差界不满足），不是已知攻击。所以既不得写「double 会被利用」，也不得反向写「double 是安全的」。中间只允许一句：「界上有多少位缺口，对应每密钥查询预算多少」。
- **WASM 侧**：浏览器是明示非机密环境，T2 在此记为已知边界，不列为阻塞项（§9 第 1 条）。

**T3（高斯采样器）**——样本量下界已有文献依据，但本仓尚未实测。

- 泄漏对象：采样树选中节点下标、消耗的 64-bit 字数，二者均依赖私钥。
- 样本量下界：R9 在 PQClean F-512 `-O3` + Cortex-M4 上报告至多 34 次签名（中位 11）恢复全部 50 个密钥，且绕开 LLL/BKZ。本仓的 TVLA 样本量以此为下界，不凭感觉设定。
- 实验构造：① 固定 vs 随机两组，分别记录节点下标与字消耗；② 报 `|t|`、样本量、runtime、commit、至少 3 次重复运行的区间；③ 逐处审计秘密索引的表查表，给文件行号。
- 失败口径：若本仓 runtime 上达不到 R9 下界对应的区分度，写 `unquantified` 并写明卡点（样本量不足、runtime 不支持、还是测量协议不覆盖），不写“未检出即安全”。
- 边界：R9 的数字是 PQClean/Cortex-M4 上的文献结果，不是本仓实测；T3 状态列仍为“未开始”，补的是判据，不是结论。

**T11（RCDT 表位翻转）**——最容易写出「已缓解」而未测的一条。
- 机制：采样分布表在可写内存里，单比特翻转使输出分布偏斜；R5 的结论是足够多签名后可恢复整钥，并给出若干廉价缓解。
- 判据：① 每个部署目标（Node 进程、WASM、原生 addon）分别写明内存完整性假设——**这是假设，不是测量**；② 把「拒绝异常短签名」这条缓解在验证端**测出来**（构造短签名，断言拒绝），在签名端明确**不做**过滤（过滤会破坏采样分布，§9 第 5 条）；③ API 暴露严格验证模式；④ 互操作核对交集成方，并写进集成文档。
- 如果我们无法在某个目标上施加缓解，**记录决策与理由**，不写「已处理」。状态只能写 `not mitigated`，并写三件事：该目标暴露的是什么、为什么不施加、影响面多大。没有理由的「可接受风险」同样不算记录。

### 5.3 两条边界引用（各一句，不展开）

- **R11（ML-KEM 密钥重用审计）**：R11 的 signal leakage 攻击在专用加固之后仍然成立，所以本文涉及密钥重用的边界（T6 的 salt 与密钥隔离、T9 的共享依赖）以这类攻击为审计参照系——**参照系，不是本仓结论**；本仓的密钥重用策略尚未评估。
- **R12（格签名第三条路线）**：R12 用高斯卷积替代 flooding 与拒绝采样、无 abort，是 Falcon 类格签名之外的第三条路线。本文的 T1/T3 只覆盖拒绝采样采样器，**不覆盖 R12 的证明结构**，也不对其安全性作任何陈述。

## 6. 评估计划

### 6.1 测量协议（所有威胁共用）

1. **先测量，后句子**：任何公开陈述之前必须存在一次运行，带日期、commit、命令，格式对齐仓内既有 TSR / KAT 锚点。
2. **泄漏检测**：dudect 风格固定 vs 随机，沿用项目既有阈值 `|t| < 4.5`；报告**样本量**与失败详情，不只报「通过」。
3. **报告口径**：`|t|` 是**单次运行的一个数**，同一份代码在同一台机器上会漂移（NTT 16–86、invNTT 0.92–25 均已实测）。所以：单个数字不构成结论，必须给出至少 3 次重复运行的区间与主机信息。
4. **每条结论必须能回答**：在哪个 runtime（Node 版本 / WASM / 原生）、哪个 commit、多少样本、几次重复。

| T2 | 分支/索引清单审计 + FFT dudect + 精度界 | 审计覆盖 100% 秘密路径分支；dudect 3 次重复均 < 4.5；精度界达标 | 报区间与缺口位数 |
| T3 | 节点下标 / 字数 TVLA | 同上 | 同 T1，另见 §5.2 T3 的失败口径 |
| T4 | 指定点位模拟位翻转 | 覆盖的故障集内**无**错误签名释放 | 列出故障集外未覆盖的点位 |
| T5 | keygen 时间分布 | 分布不可区分，或给出泄漏率 | 写泄漏率与其可利用性判据 |
| T6 | API 审查 + RNG 失败注入 | 默认 hedged；RNG 失败必致命；`deterministic: true` 在测试外被 CI 静态拦截 | 任何一项不满足即阻塞发布 |
| T7 | 对抗式编码 fuzz | 每次验证有硬上限，实测最坏值 | 报最坏值与触发输入 |
| T8 | 第二实现交叉核 + 负向测试集 | 两实现对同一输入判定一致 | 分歧即列为不兼容 |
| T9 | 依赖图 + 引用既有证据 | 每个依赖都有出处，且注明版本 | 缺证据的依赖标 `unknown` |
| T10 | 声明登记表审查 | 每条公开句子都有测量链接 | 删除该句，不软化措辞 |
| T11 | 内存假设表 + 短签名拒绝测试 | 每个目标写明假设；验证端拒绝测试通过 | 记录未施加缓解的决策 |

### 6.2.1 结论句式（统一模板，逐条覆盖 T1–T11）

只用三种句式，不许自创：

1. **泄漏类测量**（T1、T2、T3、T5）：`在 <runtime>、<commit>、<样本量>、<重复次数> 下，未检出 <泄漏类型>。` 禁用同义替换：不写「安全」「无泄漏」「恒定时间」。
2. **故障类**（T4、T11 的注入部分）：`在故障集 F 下，未观察到错误签名被释放。` 禁用：「抗故障」「免疫」。
3. **审查/测量项**（T6–T10，以及 T11 的内存完整性部分）：这些不是泄漏测量，不许套用上面两句，写 `在 <runtime>、<commit> 下，未检出 <问题>。` 若前提本身就是不可测的假设（例如某部署目标的内存完整性），写「假设：<内容>；未施加缓解，决策与理由见 <位置>」。

未达判据一律写 `unquantified`，并在同一句写明卡点（样本量不足 / runtime 不支持 / 测量协议不覆盖）。

与 §6.2 的分工：句式以本节为准，处置以 §6.2 的「不满足时」列为准；两处口径冲突时，先修正本表而不是就地妥协。

| 威胁 | 句式 | `<泄漏类型>` / `<问题>` 的取值 |
| --- | --- | --- |
| T1 | 1 | 拒绝循环迭代次数与私钥范数的相关性 |
| T2 | 1 | FFT 路径的数据相关时间差异（精度线另报每密钥查询预算） |
| T3 | 1 | 采样树节点下标与 64-bit 字消耗的密钥相关差异 |
| T4 | 2 | —（故障集 F 按点位逐条列出） |
| T5 | 1 | keygen 时间对被接受 (f, g) 形状的依赖 |
| T6 | 3 | salt 重复或可预测、RNG 失败不致命 |
| T7 | 3 | 畸形编码导致的验证工作量超限 |
| T8 | 3 | 多编码歧义与越界值被解析器接受 |
| T9 | 3 | 共享依赖中缺失出处的性质 |
| T10 | 3 | 公开陈述缺少对应测量记录 |
| T11 | 2 + 3 | 位翻转下的分布偏斜（故障集）；内存完整性（假设） |

### 6.3 定量口径（R6 怎么用）

R6 给出的是**成本模型**，不是任何实现泄漏的测量：Falcon-512 上泄露 400 个 f 的系数，可把所需 BKZ 块大小从 >350 降到 38，恢复时间约 6 小时。用法：把 T1 实测到的迭代次数分布折算成「每次签名泄露多少比特的提示」，再代进这个模型，得到攻击者需要的签名次数。**如果折算链条上任何一步只能估不能算，结论就是 `unquantified`。**

### 6.4 故障模型声明（T4 / T11 共用）

- 我们声明覆盖：在**指定点位、指定翻转方式**下注入的故障（点位清单随实现给出）。
- 我们不声明覆盖：未列出的点位、多比特故障、时序故障、以及宿主层面的内存持久性故障（后者只作为假设写进 T11）。
- 结论句式固定：「在故障集 F 下，未观察到错误签名被释放。」不得简写为「抗故障」。

### 6.5 首次测量记录（2026-11-20，第三方实现；不是本仓实现结论）

**测的是什么对象。** 本仓没有任何 Falcon 代码（§3.1），所以这里测的不是"我们的实现"，而是仓内**唯一可达**的 Falcon 代码路径：`@noble/post-quantum` 0.7.1 的 `falcon512`（`falcon.js` 上游 sha256 `0db64ec731a1bd98215b7d43bf8ce74101202354752904b2e7a703cf9276368e`）。这一节的用词一律限定在该对象上：它标定的是**测量协议与采样器的行为**，不是 FIBEMATE 未来实现的证据，也不能拿来支撑"我们支持 Falcon"。

**为什么可以用计数器代替计时。** T1 与 T3 的泄漏对象都是**离散计数**：外层候选循环跑了几轮、内层 SamplerZ 循环跑了几轮、从采样流里取走了多少字节。这些都是与平台无关的可复现量，因此可以在一台 Windows 笔记本上测得有意义的结果；计时类结论（dudect 墙钟）不在此列，本轮**没有**做。

**方法。** 在 `node_modules/@noble/post-quantum-instr/` 放一份包副本并只对副本插桩（项目本身不 import 该包，`npm ci` 会清掉副本）；插桩四处计数器：`candidates`（外层候选循环轮次）、`samplerIter`（内层 SamplerZ 迭代）、`words`（从 48 字节 ChaCha20 流取走的字节数之和）、`refills`（流重填次数）。每次签名用不同消息与不同 48 字节 `extraEntropy`。

**三次独立抽样。** 每次：固定密钥 20,000 次签名 + 100 个密钥各 200 次（共 20,000 次）。三次之间用 `RUN_TAG` 把消息与 salt 下标整体偏移 10^7，避免三次跑同一批输入。这一点是踩过的坑：第一版三次"重复"返回**完全相同**的数字，区间是 `[x, x]`，那种重复只证明代码确定性，不能当稳定性证据。

| 量 | run 1 | run 2 | run 3 | 区间 |
| --- | --- | --- | --- | --- |
| `candidates` 每签名均值 | 1 | 1 | 1 | 精确 1（标准差 0） |
| `samplerIter` 每签名均值 | 1778.31 | 1778.73 | 1778.33 | 1778.31 - 1778.73 |
| `words` 每签名均值 | 19568.35 | 19572.99 | 19568.66 | 19568.35 - 19572.99 |
| `refills` 每签名均值 | 39.146 | 39.160 | 39.146 | 39.146 - 39.160 |
| `samplerIter` 固定 vs 随机 Welch t | -0.204 | +0.642 | -1.427 | abs(t) <= 1.43 |
| `words` 的 t | -0.200 | +0.650 | -1.424 | abs(t) <= 1.42 |
| `refills` 的 t | -0.323 | +0.800 | -1.487 | abs(t) <= 1.49 |
| 跨密钥均值离散度（`samplerIter`，极差/均值） | 0.76% | 0.73% | 0.66% | <= 0.76% |

**T1 的第一轮结果：120,000 次签名里外层候选循环从未拒绝。** 第二轮（§6.6）放大到 300,000 次后拿到了 2 次拒绝，所以下面这段要连着 §6.6 读：真正成立的结论不是"没泄漏"，而是"这个实现的 T1 信道在可观测规模上几乎退化，不是零"。第一轮**从未拒绝**（每签名恰好 1 个候选，`normRejects = 0`、`lenRejects = 0`）。同时 `||s||²` 的均值是 `0.826 x beta²`、三次最大值 0.974 / 0.978 / 0.9915 x beta²：上界就压在分布尾部上，但尾部极薄。按 0/120,000 的泊松近似，拒绝率 95% 上界 `2.5 x 10^-5`。后果有两面：

- 在 12 万次样本的规模上，外层循环看不到可观测的迭代次数差异：迭代数恒为 1，所以这一轮无法据此谈"候选数"信道。这条只能在 §6.6 的 30 万次结果之上理解，不能单独引用。
- 也意味着第一轮**没有把判据压到**：要在 95% 置信度下区分 `10^-5` 量级的拒绝率，需要 `3 x 10^5` 次以上的签名（本机约 3.3 ms/次，即 17 分钟以上）。这一轮按 §6.2.1 只能记 `unquantified`；第二轮已完成该放大，见 §6.6。

**T3 的首次结果。** 三次独立抽样中，`samplerIter` / `words` / `refills` 的固定 vs 随机 `abs(t)` 全部 <= 1.49，远低于项目阈值 4.5；跨 100 个密钥的每密钥均值极差不超过 0.76%。按 §6.2.1 句式 1，可以写：**在 node v22.22.3 / win32-x64、`@noble/post-quantum` 0.7.1 `falcon512`、每次 40,000 次签名（固定 1 密钥 / 随机 100 密钥）、3 次独立抽样下，未检出采样树迭代次数与 64-bit 字消耗的密钥相关差异（`abs(t) <= 1.49`）。** 这句话**不外推**到：Cortex-M4、C 实现、原生 addon、时间维度。

**这一节明确不成立的推论（写下来防止被引用错）。**

1. 不成立"Falcon 的 T3 已通过"：R9 的 34 次签名下界是在 PQClean F-512 `-O3` + Cortex-M4 上测的，本仓既没有复现该平台，也没有跑表审计。
2. 不成立"计数器无差异 = 恒定时间"：内存访问模式、缓存行、分支预测与硬件层效应都不在这些计数器里；T2 的那一半（FFT 路径 dudect）本轮未做。
3. 不成立"noble 的实现是安全的"：本轮只覆盖两个计数器面在 20k 样本下的可区分性，没有做精度界、没有做故障注入、没有做 RCDT 内存假设。

**下一步（按可执行性排序）。** ① 把单轮样本加到 `3 x 10^5` 以给出拒绝率点估计（后台可跑，无需改代码）；② 在同一 harness 上补 FFT 路径的计时 dudect（同一进程内固定/随机两组的墙钟采样，样本量按 §6.1）；③ 若要 R9 可比，改在 PQClean C 参考实现上重跑本协议（需要 Linux + gcc，结论只对该平台成立）；④ 表审计（秘密索引查表）与 RCDT 内存假设表仍为空白，未开始。

### 6.6 第二轮：300,000 次抽样（T1 拒绝率的点估计）

§6.5 的第一轮只给出上界，因为 120,000 次里一次拒绝都没有。第二轮把单次抽样放大到 300,000 次（`RUN_TAG=9`，固定密钥 150,000 次 + 300 个密钥各 500 次 / 共 150,000 次，同机同 harness，3.31 ms/次，合计约 16.6 分钟），第一次拿到拒绝样本。

| 量 | 取值 |
| --- | --- |
| 候选总数 / 签名总数 | 300,002 / 300,000 |
| 外层拒绝 | **2 次**（均为范数拒绝，编码长度拒绝 0 次；固定组 1 次、随机组 1 次） |
| 拒绝率 | `6.67 x 10^-6`，95% CI `[8.1 x 10^-7, 2.4 x 10^-5]`（事件数 2 的泊松精确区间） |
| 折算 | 约每 150,000 次签名一次拒绝（区间 41,000 - 1,240,000） |
| 被拒候选的最大 `\|\|s\|\|²` | 34,326,042 = `1.0086 x beta²`（超界 0.86%） |
| 接受候选的 `\|\|s\|\|²` 均值 | `0.8265 x beta²` |

**这修正了 §6.5 的一句话，也修正了它的框架。** 准确的说法是：外层拒绝循环在可观测规模上**几乎**退化，但不是零——每 15 万次签名左右会迭代到第二个候选。因此 T1 的信道在原理上存在，只是单位代价极高。上一轮"120,000 次从未拒绝"的表述已按本轮实测更新，不再单独引用。

**对 T1 判据的意义。** 判据第一次被真正压到：两个拒绝样本给出了率与区间，R6 成本折算**已有输入**（每 15 万次签名一次可观测拒绝，与 R9 在 Cortex-M4 上"至多 34 次签名"的功率分析下界差约四个数量级）。折算本身仍未完成，故 §5.1 的 T1 状态仍是"首次测量"，不写成"已通过"。

**T3 面在同一次抽样里的复核。** `samplerIter` 均值 1778.76（固定）/ 1778.54（随机），`t = 1.60`；`words` 19573.3 / 19570.9，`t = 1.61`；`refills` 39.157 / 39.153，`t = 1.19`；跨 300 个密钥的每密钥均值极差不超过 0.52%。仍然低于阈值 4.5，但**样本量翻四倍后 `t` 从 1.5 量级升到 1.6 量级**，这件事本身说明："未检出"必须连同样本量一起写，否则读者无法区分"没有差异"和"差异小于这批样本的分辨率"。要把 0.01% 量级的两组均值差与噪声分开，单组还需约 `10^6` 次签名（本机约 55 分钟）。

### 6.7 T2 首次尝试：墙钟测量在本环境不可定界（`unquantified`）

T2 的机制是浮点 FFT 的中间值影响执行代价，可观测对象是**时间**。所以这一节测时间，不测计数器；而结论是：**在这台机器上，用 Node 的墙钟测这条路走不通，而且按 4.5 阈值判会判出假阳性。**

**协议。** `performance.now()` 采样每次签名的墙钟；固定密钥一组、300 个密钥一组，两组**在调用层面随机穿插**（防止慢漂移整段落进某一组）。100,000 次签名/组，3.09 ms 中位数。第一次跑到 30,000 次/组时 `t = -1.95`，看起来"未检出"；放大到 100,000 次/组，`t = 8.19`。

**`t = 8.19` 不是泄漏，是漂移。** 把每组切成 5 段、每段 20,000 次，同一份数据里：

| 段 | 固定组均值 (ms) | 随机组均值 (ms) | `t` |
| --- | --- | --- | --- |
| 1 | 3.1158 | 3.1173 | -0.22 |
| 2 | 3.1082 | 3.1121 | -0.54 |
| 3 | 3.1985 | 3.1654 | +3.75 |
| 4 | 3.1282 | 3.1857 | -7.21 |
| 5 | 3.6212 | 3.4431 | +20.37 |

两组的段均值一起往上走（固定组从 3.116 涨到 3.621，+16.2%），而**同一段内两组的差始终在 2% 以内**，`t` 的符号还来回翻。这是环境漂移的签名，不是密钥相关差异的签名。

**于是得到两条判据，比这一次的数字更有用：**

1. **dudect 的 4.5 阈值不能直接搬到墙钟上。** 同一份数据，整体 `t = 8.19` 已经"越过阈值"，但分段符号翻转说明它是漂移累积出来的。没有分段检验（或配对/去趋势设计）的墙钟 TVLA，`t > 4.5` 只是噪声够多，不是泄漏够真。
2. **"未检出"和"不可定界"是两句话。** 30,000 次/组时写"未检出"是错的，因为当时的样本分辨率根本不够；100,000 次/组时整体 `t` 越过阈值，写"检出"同样是错的。正确记法是 `unquantified`：**当前环境无法分辨 0.5% 量级的两组均值差**。

**为什么这台机器上注定定不了界。** 两次运行之间还夹着后台维护任务，机器不是安静的；JS 有 JIT 与 GC，单次签名内分配会让分布长尾（p99 是 5.5 ms，p50 是 3.09 ms）；而 T2 要分辨的效应在原生实现上是亚百分比量级。用这种观测层去碰瓷 Cortex-M4 的周期计数，只会得到"看起来有差异"的伪结论。

**下一步不在这台机器上。** 要给出 T2 的界，至少有两条路，都不在 JS 墙钟里：① 在 PQClean C 参考实现上跑本协议，用 `rdtsc`/PMU 周期计数并对齐到固定频率（同 R9 的平台，才算 apples-to-apples）；② 直接做数据依赖审计——把 FFT 路径中与秘密相关的比较、取整、归一化分支逐处列出，能被密钥触发的写成故障集/泄漏集，不能触发的写明理由。两条路都还没开始。

## 7. 明确的非声明

- **不声称恒定时间**——除非有测量，且必须写明是哪个 runtime。
- **不声称符合 FIPS 206**：标准未发布、无 NIST 向量、无 ACVP 套件（第 2 节）。
- **不因为依赖流行、或因为它出现在打包里就算被审计过。**
- **不写「无泄漏」**。诚实形式只有两种：「在此样本量下未检出泄漏」或「泄漏率测得为 X」。
- **不声称「去掉浮点就安全」**：为了省事替换高斯采样器，是已知的丢掉安全论证的方式（R5 讨论了这么做的方案）。
- **不声称 double 精度可被利用**：R7 只证明界上的缺口，且明说无已知实际攻击。
- **不声称覆盖尚未出现的攻击方式。** 密码学分析是动态的：若未来出现涉及 T1–T11 之外攻击面的成果，本模型自动失效，必须重新评估后才能继续引用。

**逐条对照（2026-11-19）**：上述禁语已对着 T1–T11 逐条检查过一次。核对口径是「出现在哪种语境」，不是「有没有出现过」——这些词在禁用与否认句里必然出现，判据是**有没有一处把它们当作结论或状态**。

- 「恒定时间」（7 行）：全在禁用句或**要求**句——第 1 节「不是」、T2/T5 证据栏要实现的目标、T10 反面例子、§6.2.1 禁用清单、§7 禁令、本节；**对本实现作为结论 0 处**。
- 「抗故障」（4 行）：全在禁用语与替代说明；**作为实现属性 0 处**。
- 「无泄漏」（3 行）：全在禁用说明与反面句式；**作为结论 0 处**。

## 9. 设计原则（2026-11-18 已确认，正文不留 open question）

1. **WASM 是明示的非机密环境**：前端不处理长期私钥；浏览器侧签名走 WebCrypto 或安全硬件。T2 在 WASM 侧记为已知边界，不是阻塞项。
2. **默认 hedged**：`deterministic: true` 仅供测试，文档与代码注释均标「生产禁用」，CI 加静态检查拦截测试外使用。
3. **T1 的泄漏界由独立读者签字**：外部密码学专家，或项目内不负责该模块的架构师；采样器作者不得自签。
4. **威胁模型在移植落地前公开发布**，并明写「这是实现之前的假设与计划」，避免把「尚未实现」读成「已测量」。
5. **T11 按角色区分**：验证端拒绝异常短签名；签名端不过滤以保分布；API 提供严格验证模式；互操作核对交集成方。
