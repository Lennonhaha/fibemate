## 0. 三条规定

1. **没有量化就写 unquantified。** 任何形容词（「稳健」「安全」「已加固」）都不能替代一次测量。
2. **只声明覆盖的故障模型，不写 fault proof。** 结论的正确形式是「在这组注入故障下没有释放错误签名」，不是「抗故障」。
3. **引用逐条回源。** 标题、作者、venue、年份从 ePrint 或出版方页面抄，参考文献表记录核对日期；核不到的引用直接删，不软化。

## 1. 本文是什么、不是什么

**是**：一个 Falcon 签名路径的**范围界定与取证计划**，写在任何移植落地之前，目的是让评估标准先于实现存在——否则实现会悄悄定义标准。

**不是**：安全证明、新的密码分析、对任何第三方库的审计、「恒定时间」声明、FIPS 206 合规声明。

### 3.2 这些事实支持与不支持什么

- **支持**：本项目目前没有任何自研 Falcon 代码，因此不存在「我们的实现已通过 X」这类陈述的成立条件；任何关于 Falcon 的行为描述都只能来自规格与文献。
- **支持**：`www/noble-pq/index.js` 引用的第三方实现，是这个仓库里**唯一**可达的 Falcon 代码路径。
- **不支持**：「我们支持 Falcon」。引用一个库不等于实现它，也不等于评估过它。
- **不支持**：把站点里那份第三方实现当成基线来写安全结论——它未被本项目评估过，且运行在明示非机密的浏览器环境（见 §9 第 1 条）。

### 3.3 依赖事实

- `@noble/post-quantum` 是外部依赖，随站点打包；本文只声明「它存在且被引用」，不声明其侧信道属性。
- Falcon 的采样器依赖 SHAKE-256 / RNG；这两条路径与现有 ML-KEM/ML-DSA/SLH-DSA 共享，属于 T9 的依赖面。

## 4. 资产与对手模型

**资产**：NTRU 私钥基 (f, g, F, G)；每次签名的 salt；由私钥导出的 FFT 中间值；接受/拒绝判定及其迭代次数。

| ID | 对手 | 能力 | 现实信道 |
| --- | --- | --- | --- |
| A1 | 远程 | 提交待签消息，观察墙钟时间与响应 | 网络计时，粒度粗 |
| A2 | 同机非 root | 同宿主跑代码 | 缓存（prime+probe）、缺页、调度计时 |
| A3 | 本地非特权 | 可读性能计数器（若有权限） | 分支误预测、缓存缺失、指令计数 |
| A4 | 物理接触 | 持有或借用设备 | 功耗/电磁迹，无屏蔽时可单迹 |
| A5 | 故障注入 | 时钟/电压/激光，或投毒的依赖 | FFT、采样器、范数检查处的位翻转 |
| A6 | 坏 RNG | salt 或采样字重复/可预测 | 重复或偏斜的签名 |
| A7 | 集成误用 | API 接错 | 缺 salt、跨方案复用密钥、验证工作量不限 |

**能力边界（写进本文就是承诺）**：不建模「对手能改我们的源代码仓库」；不建模「对手控制宿主的 RNG 且我们无法检测」——后者按 A6 处理，要求**失败必须响亮**（§6.4）。

### 5.2 逐条判据（关键三条展开，其余按表执行）

**T1（拒绝循环）**——最容易被「实现细节」掩盖的一条。
- 泄漏对象不是迭代次数本身，而是**迭代次数与私钥范数的相关性**。所以证据必须是分布，不是平均值。
- 判据：① 10^5 次签名的迭代次数直方图（按私钥固定 / 按密钥集随机两组）；② 循环计数上的固定 vs 随机 TVLA，报样本量与 |t|；③ 用 R6 的提示攻击成本模型把分布折算成「攻击者需要多少次签名、BKZ 块大小降到多少」。
- **泄漏界必须由独立读者签字**（§9 第 3 条）：采样器作者不得自签。
- **资源受限时的退路（不等于免签）**：确实找不到外部密码学专家时，由项目内**不负责该模块的作者**（主架构师或 CTO）独立复核并出具**书面**意见；签字人与采样器作者不得是同一人，意见里必须写明「资源受限下的替代签字」。这条只降低门槛，不取消签字本身。
- 如果折算不出数字，写 `unquantified`，并说明卡在哪一步——「unquantified」与「安全」是两句话。

**T2（浮点精度与 FFT 暴露）**——两条独立的线，不要混为一谈。
- **实现暴露线**：实现在浮点上做 FFT，中间值直接由私钥派生；R1 在 Cortex-M4 上用约 10k 条差分 EM 迹恢复密钥，R2 用单条功耗迹在 `-O0/-Os/-O3` 下报告 100% 恢复（PQClean 目标）、对内嵌汇编目标 10 条迹恢复 53/100 个密钥。这两条说明的是**未受保护实现的暴露性**，不是我们的实现的结论。
- **精度线**：R7 指出标准 double（53 bit）**不满足**安全高斯采样器所需的已证误差界，三字算术（≥72 bit）满足，代价约 1.84×。
- **2026-11-19 追加（R8）**：R8 把这条缺口量成了查询预算——双精度下每个密钥可用的签名查询约 2^61.5（Falcon-512）/2^58.7（Falcon-1024），低于 2^64 目标；32.64 定点实现达 2^99.7/2^96.7。这不是「double 可被利用」的证据，而是「缺口有多大」的证据。所以 T2 的判据在②之外再加一项：**报出所选精度下的每密钥查询预算，并写明它相对目标安全级的余量**。
- 判据：① FFT 路径按引用逐分支审计（列出分支与内存索引，给文件行号，是清单不是结论）；② 该路径 dudect；③ 精度需求写成已证界 + 本文档声明它需要多少位。
- **本文不声称 double 可被利用**：R7 自己写明目前没有已知的实际攻击。我们报告「界上的缺口」，不多说一个字。
- **WASM 侧**：浏览器是明示非机密环境，T2 在此记为已知边界，不列为阻塞项（§9 第 1 条）。

**T3（高斯采样器）**——样本量下界已有文献依据，但本仓尚未实测。

- 泄漏对象：采样树选中节点下标、消耗的 64-bit 字数，二者均依赖私钥。
- 样本量下界：R9 在 PQClean F-512 `-O3` + Cortex-M4 上报告至多 34 次签名（中位 11）恢复全部 50 个密钥，且绕开 LLL/BKZ。本仓的 TVLA 样本量以此为下界，不凭感觉设定。
- 实验构造：① 固定 vs 随机两组，分别记录节点下标与字消耗；② 报 `|t|`、样本量、runtime、commit、至少 3 次重复运行的区间；③ 逐处审计秘密索引的表查表，给文件行号。
- 失败口径：若本仓 runtime 上达不到 R9 下界对应的区分度，写 `unquantified` 并写明卡点（样本量不足、runtime 不支持、还是测量协议不覆盖），不写“未检出即安全”。
- 边界：R9 的数字是 PQClean/Cortex-M4 上的文献结果，不是本仓实测；T3 状态列仍为“未开始”，补的是判据，不是结论。

**T11（RCDT 表位翻转）**——最容易写出「已缓解」而未测的一条。
- 机制：采样分布表在可写内存里，单比特翻转使输出分布偏斜；R5 的结论是足够多签名后可恢复整钥，并给出若干廉价缓解。
- 判据：① 每个部署目标（Node 进程、WASM、原生 addon）分别写明内存完整性假设——**这是假设，不是测量**；② 把「拒绝异常短签名」这条缓解在验证端**测出来**（构造短签名，断言拒绝），在签名端明确**不做**过滤（过滤会破坏采样分布，§9 第 5 条）；③ API 暴露严格验证模式；④ 互操作核对交集成方，并写进集成文档。
- 如果我们无法在某个目标上施加缓解，**记录决策与理由**，不写「已处理」。

### 5.3 两条边界引用（各一句，不展开）

- **R11（ML-KEM 密钥重用审计）**：R11 的 signal leakage 攻击在专用加固之后仍然成立，所以本文涉及密钥重用的边界（T6 的 salt 与密钥隔离、T9 的共享依赖）以这类攻击为审计参照系——**参照系，不是本仓结论**；本仓的密钥重用策略尚未评估。
- **R12（格签名第三条路线）**：R12 用高斯卷积替代 flooding 与拒绝采样、无 abort，是 Falcon 类格签名之外的第三条路线。本文的 T1/T3 只覆盖拒绝采样采样器，**不覆盖 R12 的证明结构**，也不对其安全性作任何陈述。

## 6. 评估计划

### 6.1 测量协议（所有威胁共用）

1. **先测量，后句子**：任何公开陈述之前必须存在一次运行，带日期、commit、命令，格式对齐仓内既有 TSR / KAT 锚点。
2. **泄漏检测**：dudect 风格固定 vs 随机，沿用项目既有阈值 `|t| < 4.5`；报告**样本量**与失败详情，不只报「通过」。
3. **报告口径**：`|t|` 是**单次运行的一个数**，同一份代码在同一台机器上会漂移（NTT 16–86、invNTT 0.92–25 均已实测）。所以：单个数字不构成结论，必须给出至少 3 次重复运行的区间与主机信息。
4. **每条结论必须能回答**：在哪个 runtime（Node 版本 / WASM / 原生）、哪个 commit、多少样本、几次重复。

### 6.2 威胁 → 实验映射

本表只管「做什么」与「不满足时怎么处置」；结论怎么写由 §6.2.1 决定，两边不重复表述。

### 6.2.1 结论句式（统一模板，逐条覆盖 T1–T11）

只用三种句式，不许自创：

1. **泄漏类测量**（T1、T2、T3、T5）：`在 <runtime>、<commit>、<样本量>、<重复次数> 下，未检出 <泄漏类型>。` 禁用同义替换：不写「安全」「无泄漏」「恒定时间」。
2. **故障类**（T4、T11 的注入部分）：`在故障集 F 下，未观察到错误签名被释放。` 禁用：「抗故障」「免疫」。
3. **审查/测量项**（T6–T10，以及 T11 的内存完整性部分）：这些不是泄漏测量，不许套用上面两句，写 `在 <runtime>、<commit> 下，未检出 <问题>。` 若前提本身就是不可测的假设（例如某部署目标的内存完整性），写「假设：<内容>；未施加缓解，决策与理由见 <位置>」。

未达判据一律写 `unquantified`，并在同一句写明卡点（样本量不足 / runtime 不支持 / 测量协议不覆盖）。

与 §6.2 的分工：句式以本节为准，处置以 §6.2 的「不满足时」列为准；两处口径冲突时，先修正本表而不是就地妥协。

| 威胁 | 句式 | `<泄漏类型>` / `<问题>` 的取值 |
| --- | --- | --- |
| T1 | 1 | 拒绝循环迭代次数与私钥范数的相关性 |
| T2 | 1 | FFT 路径的数据相关时间差异（精度线另报每密钥查询预算） |
| T3 | 1 | 采样树节点下标与 64-bit 字消耗的密钥相关差异 |
| T4 | 2 | —（故障集 F 按点位逐条列出） |

| T6 | 3 | salt 重复或可预测、RNG 失败不致命 |
| T7 | 3 | 畸形编码导致的验证工作量超限 |

### 6.3 定量口径（R6 怎么用）

R6 给出的是**成本模型**，不是任何实现泄漏的测量：Falcon-512 上泄露 400 个 f 的系数，可把所需 BKZ 块大小从 >350 降到 38，恢复时间约 6 小时。用法：把 T1 实测到的迭代次数分布折算成「每次签名泄露多少比特的提示」，再代进这个模型，得到攻击者需要的签名次数。**如果折算链条上任何一步只能估不能算，结论就是 `unquantified`。**

### 6.4 故障模型声明（T4 / T11 共用）

- 我们声明覆盖：在**指定点位、指定翻转方式**下注入的故障（点位清单随实现给出）。
- 我们不声明覆盖：未列出的点位、多比特故障、时序故障、以及宿主层面的内存持久性故障（后者只作为假设写进 T11）。
- 结论句式固定：「在故障集 F 下，未观察到错误签名被释放。」不得简写为「抗故障」。

## 7. 明确的非声明

- **不声称恒定时间**——除非有测量，且必须写明是哪个 runtime。
- **不声称符合 FIPS 206**：标准未发布、无 NIST 向量、无 ACVP 套件（第 2 节）。
- **不因为依赖流行、或因为它出现在打包里就算被审计过。**
- **不写「无泄漏」**。诚实形式只有两种：「在此样本量下未检出泄漏」或「泄漏率测得为 X」。
- **不声称「去掉浮点就安全」**：为了省事替换高斯采样器，是已知的丢掉安全论证的方式（R5 讨论了这么做的方案）。
- **不声称 double 精度可被利用**：R7 只证明界上的缺口，且明说无已知实际攻击。
- **不声称覆盖尚未出现的攻击方式。** 密码学分析是动态的：若未来出现涉及 T1–T11 之外攻击面的成果，本模型自动失效，必须重新评估后才能继续引用。

**逐条对照（2026-11-19）**：上述禁语已对着 T1–T11 逐条检查过一次。核对口径是「出现在哪种语境」，不是「有没有出现过」——这些词在禁用与否认句里必然出现，判据是**有没有一处把它们当作结论或状态**。

- 「恒定时间」（7 行）：全在禁用句或**要求**句——第 1 节「不是」、T2/T5 证据栏要实现的目标、T10 反面例子、§6.2.1 禁用清单、§7 禁令、本节；**对本实现作为结论 0 处**。
- 「抗故障」（4 行）：全在禁用语与替代说明；**作为实现属性 0 处**。
- 「无泄漏」（3 行）：全在禁用说明与反面句式；**作为结论 0 处**。
- 「FIPS 206 合规」（2 行）：均为「不声称」或与其绑定的自我作废条款；**作为声明 0 处**。
- 「double 可被利用」（3 行）：均为否定句或对 R8 查询预算的转述；**作为结论 0 处**。
- 「已缓解」（4 行）：均为「不得写」类禁令与反面说明；**作为状态列取值 0 处**。
- R12 在 §5.3 只作候选对照，本文不对其安全性作任何陈述。

## 9. 设计原则（2026-11-18 已确认，正文不留 open question）

1. **WASM 是明示的非机密环境**：前端不处理长期私钥；浏览器侧签名走 WebCrypto 或安全硬件。T2 在 WASM 侧记为已知边界，不是阻塞项。
2. **默认 hedged**：`deterministic: true` 仅供测试，文档与代码注释均标「生产禁用」，CI 加静态检查拦截测试外使用。
3. **T1 的泄漏界由独立读者签字**：外部密码学专家，或项目内不负责该模块的架构师；采样器作者不得自签。
4. **威胁模型在移植落地前公开发布**，并明写「这是实现之前的假设与计划」，避免把「尚未实现」读成「已测量」。
5. **T11 按角色区分**：验证端拒绝异常短签名；签名端不过滤以保分布；API 提供严格验证模式；互操作核对交集成方。
