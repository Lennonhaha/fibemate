## 一、现状：FIBEMATE 已有的探测能力

本模块不是从零起步。FIBEMATE 已经具备一套可运行的 PQC 部署探测链路，本设计是在此基础上的扩展与闭环，而非新建。

### 1.1 已有资产盘点

| 资产 | 位置 | 当前能力 | 局限 |
|------|------|------|------|
| TLS 探测引擎 | `server/pqc-detector.js` | 纯 Node.js `tls` 模块探测 TLS 1.3 端点，识别 PQC NamedGroup（IANA 4584–4591），输出结构化报告 | 单端点、无批量、无持久化 |
| 探测评分模型 | 同上（`score()`） | 100 分制，5 项检查（TLS 1.3 30 分 / PQC 密钥交换 25 分 / 密码套件 15 分 / 证书 15 分 / 迁移就绪 15 分），A–F 评级 | 启发式评分，未经验证，非权威认证 |
| HTTP API 桥 | `server/pqc-probe-api.js` | localhost:9004，`/api/v1/probe`、`/probe/batch`（上限 5 目标）、`/probe/predefined`，带 CORS 白名单 | 单机、内存态、无鉴权、无存证 |
| Web 前端 | `www/docs/pqc-deployment-checker.html` | 浏览器端部署验证交互界面 | 依赖 API 桥，无历史记录 |
| PQC 仪表盘 | `www/docs/pqc-dashboard.html` + `pqc-dashboard-data.json` | 12 种算法就绪度加权评分（quantumRisk×0.6 + migrationTime×0.4） | 静态数据驱动，非实时探测 |
| CBOM 可视化 | `www/docs/cbom-viewer.html`、`cbom-graph.html`、`tools/cbom-cyclonedx.json` | 加密物料清单（CycloneDX）依赖链路可视化 | 展示为主，未与探测结果联动 |
| TSR 存证 | `docs/tsa/*.tsr`（225+ 份） | DigiCert + FreeTSA 双机构时间戳，代码/测试/文档版本固化 | 覆盖代码与文档，尚未覆盖"探测结果"这类运行时证据 |

### 1.2 关键事实：已有评分模型的边界

`pqc-detector.js` 的 `score()` 是一个**启发式检查清单**，用于快速给端点一个"PQC 就绪度"的第一印象。它：

- ✅ 能识别：TLS 版本、密钥交换是否含 PQC KEM、密码套件强度、证书公钥类型
- ❌ 不能证明：实现是否正确、是否有侧信道泄漏、密钥管理是否合规、降级攻击防护是否到位

本设计文档必须诚实标注这一点——**评分是"第一印象"，不是"审计结论"**。任何对外表述都不能把它包装成权威认证。

## 二、缺口：从"单次探测"到"可审计证据链"

基于上述现状，明确三个真实缺口：

### 2.1 探测 → 批量

当前 `probeMany()` 已支持批量，但：
- 无端点清单管理（需 CLI 传入，无配置文件、无调度）
- 无结果持久化（跑完即丢，无法横向对比、纵向追踪）

### 2.2 评分 → 存证

当前评分结果是一次性的内存对象，没有：
- 时间戳固化（探测结果无法证明"某时刻某端点状态"）
- 可追溯性（无法审计"这个结论是哪次探测、什么配置得出的"）

### 2.3 探测 → 决策

当前输出是原始报告，没有：
- 迁移建议映射（探测到的弱点如何对应到具体迁移动作）
- 与 CBOM/仪表盘的联动（探测结果未反哺到资产清单与就绪度评分）

## 三、模块功能架构

### 3.1 三层架构

```
┌─────────────────────────────────────────────────────────┐
│ 用户层                                                      │
│ Web 仪表盘  │  CLI 工具  │  GitHub Action  │  API          │
├─────────────────────────────────────────────────────────┤
│ 分析层                                                      │
│ 端点就绪度评分  │  迁移建议映射  │  TSR 存证生成  │  报告    │
├─────────────────────────────────────────────────────────┤
│ 采集层                                                      │
│ TLS 握手探测  │  端点清单管理  │  结果持久化                │
└─────────────────────────────────────────────────────────┘
```

### 3.2 核心功能模块（全部基于已有资产扩展）

| 模块 | 功能 | 复用资产 | 新增需求 |
|:---|------|:---|:---|
| **1. 批量探测 CLI** | 从清单文件批量探测端点，输出统一报告 | `pqc-detector.js` 的 `probeMany()` | 清单文件格式、调度 |
| **2. 结果持久化** | 探测结果落盘，支持横向/纵向对比 | — | JSON 存储、时间序列 |
| **3. TSR 存证闭环** | 每次探测结果生成时间戳证据 | TSR 存证流程（`docs/tsa/`） | 探测结果哈希 + 存证 |
| **4. 迁移建议映射** | 探测弱点 → 迁移动作 | `www/docs/migration-priority.html`、`PQC_MIGRATION_PLAN.md` | 规则映射表 |
| **5. 仪表盘联动** | 探测结果反哺就绪度评分 | `pqc-dashboard-data.json`、CBOM | 数据写入接口 |

### 3.3 明确不做的（诚实边界）

- ❌ 不声称"证明部署安全"——评分是启发式，非审计
- ❌ 不做被动式网络嗅探/流量分析——只做主动 TLS 握手探测
- ❌ 不做降级攻击的运行时检测——TLS 握手探测无法模拟中间人攻击，降级攻击防护属于协议实现审查，超出本模块范围
- ❌ 不接入未验证的第三方评分模型——评分规则由 FIBEMATE 自己定义并公开

## 五、用户旅程

### 5.1 典型场景：企业安全团队评估端点 PQC 就绪度

```
1. 维护端点清单（host:port 列表，JSON 或文本）
 ↓
2. 运行批量探测 CLI，逐端点 TLS 握手
 ↓
3. 每个端点输出就绪度评分（0–100，A–F 评级）
 ↓
4. 探测结果自动生成 TSR 存证（可审计的"某时刻状态"）
 ↓
5. 导出报告（含评分明细 + 迁移建议 + 存证引用）
```

### 5.2 典型场景：持续追踪迁移进度

```
1. 定期（如每周）对同一清单跑批量探测
 ↓
2. 结果持久化，形成时间序列
 ↓
3. 仪表盘展示"端点就绪度变化趋势"
 ↓
4. 安全团队据此判断迁移是否在推进
```

## 八、风险评估

| 风险 | 影响 | 缓解措施 |
|:---|:---|:---|
| 探测目标 TLS 握手超时 | 结果不完整 | 复用现有 6 秒超时 + 重试配置 |
| 评分被误读为"权威认证" | 可信度受损 | 报告/文档显著标注"启发式检查，非审计结论" |
| 目标不支持 PQC 算法 | 评分低 | 明确标注"传统算法"，区分"未检测到"与"检测到但未启用" |
| TSR 存证服务不可用 | 存证失败 | 本地存证 + 延迟补存 |
| 批量探测被目标视为扫描 | 法律/合规风险 | 仅探测用户自有端点，清单由用户提供 |

## 十、诚实声明（对外口径）

1. 本模块的"就绪度评分"是 FIBEMATE 自定义的**启发式检查清单**，用于快速发现明显问题，**不构成安全审计结论**，不替代第三方审计。
2. 探测仅覆盖 TLS 握手层的算法协商，**不覆盖**实现正确性、侧信道、密钥管理、降级攻击防护。
3. 所有评分规则公开、可复现，与 FIBEMATE"所有声明有证据支撑"的原则一致。
