# FIBEMATE 文档风格规范（STYLE_GUIDE）

> 适用范围：`docs/`、`www/docs/`、根目录 `.md`、`www/index.html` 等所有面向读者的中文文档。
> 目的：统一标点与术语写法，避免中英文标点混用、裸 `&` 误用。
> 最后更新：2026-08-13

## 一、统一标点规范

| 场景 | 规范 | 示例 |
|------|------|------|
| 文档标题分隔 | 用 `·` | `项目治理 · 决策流程 · 维护者职责` |
| 并列关系（中文） | 用 `、` 或 `与` | `依赖与安装、可复现构建` |
| 范围表示 | 用 `→` 或 `至` | `v1.0 → v3.3` 或 `v1.0 至 v3.3` |
| 代码 / 术语 | 用反引号 `` ` `` | `` `CITATION.cff` `` |
| 中文引号 | 用 `“”` | `“诚实标注纯 JS 边界”` |
| 注释说明 | 用 `「」` | `「仅供教学演示，不推荐生产」` |

## 二、禁止 / 替换规则

| 修正项 | 替换规则 | 示例 |
|--------|----------|------|
| 裸 ` & `（中文并列） | `&` → `与` / `·` / `、` | `依赖 & 安装` → `依赖与安装` |
| 半角引号（中文语境） | `"xxx"` → `“xxx”` | `"诚实标注"` → `“诚实标注”` |
| 连字符当分隔（中文） | ` - ` → ` · ` | `灾难恢复 - 备份策略` → `灾难恢复 · 备份策略` |
| 尾部冗余标点 | 删除 | `事件处置 · 上报流程，` → `事件处置 · 上报流程` |

## 三、必须保留（不可替换）

以下场景中的 `&`、`-`、`"` **一律保留**，不得按第二节规则替换：

1. **HTML 实体**：`&nbsp;` `&amp;` `&lt;` `&gt;` `&quot;` `&apos;` `&#数字;`
2. **位运算 / 逻辑运算**：`&&` `&` `|` `^` `~`（代码块内）
3. **URL 查询参数**：`?a=1&b=2`、`&redirect=`
4. **官方英文术语**：NIST CSF 的 `Detection & Analysis`、`Containment, Eradication & Recovery` 等——括号内引用原文时保留 `&`
5. **代码块 / 内联代码**：反引号与代码围栏内的内容一律不动

## 四、执行口径

- **纯中文标题 / 描述**：按第二节统一。
- **中英混排**：中文部分统一，括号内英文术语保留原文。
- **有疑问时**：优先「不破坏术语准确性」，宁可保留原文，也不要为统一而改错。

## 五、代码安全：正则 ReDoS 检查（编写新正则前必读）

> 适用范围：所有新写的正则表达式（尤其 `.js` / `.ts` 代码，不论是否面向读者）。

**禁止使用的危险模式**（回溯灾难 / ReDoS，攻击者可用恶意输入导致 CPU 飙高）：

| 危险模式 | 说明 | 安全替代 |
|----------|------|---------|
| `.*$` / `.+$`（未约束） | `.*` 与 `$` 组合，长输入下指数级回溯 | 用 `split()` / 字符类 `[^/]*$` |
| `(.+)+` / `([a-z]+)+`（嵌套量词） | 嵌套量词是 ReDoS 典型根源 | 拆成单层 |
| `(a|a)+`（重叠分支） | 分支重叠导致重复匹配 | 消除分支重叠 |

**编写新正则时的自查清单**：
1. 是否有 `.*` / `.+` 紧邻锚点 `$`？→ 改用字符类或 `split()`
2. 是否有嵌套量词 `(...+)+`？→ 拆单层
3. 是否在用户可控输入上执行？→ 优先用非正则的字符串方法（`split` / `includes` / `startsWith`）

**示例**（2026-08-13 实际修复）：
```js
// ❌ ReDoS：长路径输入会回溯
l.replace(/^https?:\/\//, '').replace(/\/.*$/, '')
// ✅ 等价无回溯
l.replace(/^https?:\/\//, '').split('/')[0]
```

## 六、代码安全：转义必须连同转义字符本身（编写 escape 函数前必读）

> 适用范围：任何把外部字符串拼进结构化文本的函数——Markdown 表格、CSV、HTML、shell、正则字面量。

**规则：转义任何分隔符之前，先转义转义字符本身。**

```js
// ❌ 只转义分隔符：输入以反斜杠结尾时，转义序列被重新打开
s.replace(/\|/g, '\\|')
//    'a\' + '|'  ->  'a\|'  ->  表格仍然在那里断列

// ✅ 先反斜杠，再分隔符
s.replace(/\\/g, '\\\\').replace(/\|/g, '\\|')
```

**实例**（2026-11-20，PR #624）：`scripts/gh-patrol.cjs` 的 `mdEscape` 只转义了 `|`。CodeQL 以 `js/incomplete-sanitization`（high）在首个 CI 的 4 秒判红，修复前该函数会把含反斜杠的 PR 标题写坏一行表格。

**为什么会漏**：只测了「普通字符串 + 分隔符」，没测「分隔符与转义字符相邻」。这类 bug 在所有转义函数里同构：

| 目标格式 | 要转义的字符 | 常见的漏项 |
|---|---|---|
| Markdown 表格 | `\` 然后 `\|` | 反斜杠 |
| CSV | `"` → `""`，含 `,` `"` 换行的字段整体加引号 | 引号嵌套、行尾反斜杠 |
| HTML | `&` 先于 `<` `>` `"` `'` | 先转 `<` 会把 `&lt;` 变成 `&amp;lt;` |
| shell 单引号 | `'` → `'\''` | 结尾单引号 |
| 正则字面量 | `\` 与元字符 | 反斜杠本身 |

**自查清单**（写 escape 函数时逐条过）：

1. 转义字符（`\`、`&`、`"`）是否**排在分隔符之前**处理？
2. 有没有一组**必须能还原**的用例：`a\|b`、`a\`、`\\|`，逐个断言 round-trip？
3. 有没有一条**负向控制**：故意传入未加保护的输入，断言输出确实会坏（否则无法证明这个函数真的在转义）？
4. 是否在用户可控输入上执行？（PR 标题、issue 正文、仓库名都算）

**判据**：一个转义函数的正确性，不体现在「普通输入看起来对」，而体现在**分隔符与转义字符相邻时仍然对**。只测前者，等于没测。
