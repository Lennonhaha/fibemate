# Deploy evidence records

One file per deployed commit, generated by [`scripts/deploy-evidence.cjs`](../../scripts/deploy-evidence.cjs):

```bash
node scripts/deploy-evidence.cjs            # resolve the commit from /health
node scripts/deploy-evidence.cjs --run <id> # also attach workflow metadata
```

The script refuses to write a record when the checks disagree — exit code 1, no file.
That refusal is the point: a directory of records that only ever contains successes, and
cannot produce a failure, would be decoration.

## What a record proves

- production served that exact commit: `/health` `build.commit` and `served.commit` both equal it;
- the bytes a visitor receives for `/` are byte-identical to `www/index.html` at that commit;
- the served manifest on disk matches the running process (`matches_process=true`).

## What a record does not prove

- **not correctness.** An aligned deploy can ship a bug. Alignment says "these bytes are live", nothing more;
- **not coverage.** Only `/` and `/health` are compared. No API, no database, no TLS config;
- **not quality.** Test results live in CI. This is an alignment record.

Each generated file repeats the two lists above, so a record read outside this directory
cannot lose the caveat.

## Where these files are, and are not

`docs/` is **not** part of the served tree — nginx serves `/opt/fibemate/current/www`.
Nothing here is reachable from `https://fibemate.net/`. These records are public only in the
sense that the repository is public; they never travel to visitors.

They are committed rather than uploaded as CI artifacts on purpose: an artifact expires and
whoever needs the record has to trust that the workflow kept it, while a committed file is
timestamped by git and can be diffed against the next one.
