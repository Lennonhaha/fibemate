## 二、VWZ 性能瓶颈确认

### 实际代码位置
- Rust 源码在 `rust/vwz-sign-wasm/src/`（**不是** `vwz/src/`）
- 分支 `experimental/vwz-lg` **本地不存在**，仅 origin + server 远程

### WASM 边界现状
- lib.rs 仅 `#[wasm_bindgen(start)] pub fn init()`
- signature.rs 暴露：keygen / keygen_seeded / sign / verify / serialize_public_key / deserialize_public_key / serialize_signature / deserialize_signature / estimate_sizes
- **无** `public_tensor_new`、**无** `verify_batch`

### 瓶颈定位（关键）
`verify()` 内部：
```rust
let pk_tensor = PubTensor::new(pk.k, pk.data.clone());  // 每次全量 clone 三维 Vec
```
- `PubTensor::new` 零拷贝（直接拿走 data），代价全在 `clone()`
- k=8 ~2.7KB，k=16 ~19KB，每次 verify 都重复

### bench_vwz.js 调用方式（已读）
```javascript
const pk = kp.public_key();          // 持有 pk 对象
verify(pk, msg, sig);                 // 复用，不重复 deserialize
```
**结论：JS 侧已复用 pk 对象 → 方向 C（JS 缓存反序列化）无收益**

### 最优方案
**方向 B：Rust 侧 `verify_batch`** —— 一次传 `pk + [(msg,sig)×N]`，Rust 只构造一次 PubTensor，循环验证 N 个，消除重复 clone + 减少 WASM 边界调用次数（N→1）。

预期：批处理场景 5-8×；单次 verify 场景需配合 PublicKey 惰性缓存（RefCell 或改签名）。

- 先做 verify_batch 还是先做 PublicKey 惰性缓存
