# SM2 WASM 重写 — 性能基准与瓶颈定位

## 时间
2026-08-13（D-18）

## 性能基准结果

| 实现 | 标量乘法耗时 | 说明 |
|------|------------|------|
| WASM（Montgomery Ladder） | 24.9 ms/op | 恒定时间，256 轮 |
| JS 生产（wNAF 窗口表） | 9.4 ms/op | 非恒定时间 |
| JS 参考（简单 BigInt） | 22.0 ms/op | 双线性 |

**结论：WASM 比 JS wNAF 慢 2.65×，但快于简单 BigInt 参考。**

## 瓶颈定位（精确 profile）

| 操作 | 耗时 | 说明 |
|------|------|------|
| montMulN（256bit CIOS） | 2.1 µs/op | 核心瓶颈 |
| montMulP（256bit CIOS） | 3.3 µs/op | 同上 |
| feInvN（Fermat 256 轮） | 0.9 ms/op | 正常 |
| u64 乘加 | 1.31 ns/op | **非瓶颈** |
| u32 乘加 | 1.35 ns/op | **非瓶颈** |

## 关键发现

### 1. u64 不是性能瓶颈
AssemblyScript 的 u64（i64）乘法在 V8 下 1.31ns，与 u32 的 1.35ns 几乎无差别。之前的假设（"u64 软件模拟极慢"）是**错误的**。

### 2. 真正的性能差距来自算法选择
- **WASM**：Montgomery Ladder（256 轮 double+add，每轮 ~6 次 montMul）→ 24.9ms
- **JS 生产**：wNAF 窗口表（预计算 16 点，~64 次点加法）→ 9.4ms

这是**恒定时间 vs 速度**的经典权衡：
- Montgomery Ladder 恒定时间（无密钥依赖分支），是 TVLA 侧信道安全的前提
- wNAF 窗口表有密钥依赖的查表访问模式，侧信道不安全（这正是 v1.3→v1.4 退化的问题，MEMORY 记录过）

### 3. 后续优化方向（恒定时间前提下）
- **Comb 方法**（固定窗口，仍恒定时间）：预计算表 + 固定迭代次数，可提速 2-4×
- **Montgomery 域优化**：减少 toMont/fromMont 转换次数
- **并行 Jacobian 坐标**：避免频繁的 feInv
- **SIMD**：WASM SIMD 指令集（128-bit）
