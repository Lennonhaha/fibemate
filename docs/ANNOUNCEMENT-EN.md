# FIBEMATE: engineering status, known gaps, and an invitation to review

FIBEMATE is an engineering verification platform for post-quantum cryptography:
implementations of ML-KEM, ML-DSA, SLH-DSA and SM2/SM3/SM4, cross-language
interoperability, a CycloneDX CBOM pipeline, and a formalization of the VWZ
construction in Isabelle/HOL.

This is not a product announcement. The reason for writing it is specific:
OpenSSF Scorecard reports **Code-Review 0** for the main repository (0 of 28
changesets had an approving review). That is a structural weakness of a
single-maintainer project, and it can only be fixed by outside reviewers.

Everything below separates what is verified, what is measured by somebody else,
and what is not done yet. Where a claim is checkable, the command or endpoint is
given.

## 1. What is enforced

Merge gates on `main` (repository ruleset, required checks):

- Seven required status checks: `lint`, `bom-check`, `bench`, `sbom`,
  `docs-check`, `dco`, `interop`.
- Branches must be up to date with the base; force-pushes and branch deletion
  are disabled; all changes go through pull requests.
- Every commit must carry a DCO `Signed-off-by` trailer. This has rejected real
  violations: the merge commit generated by GitHub's "Update branch" button
  carries no signoff, so the workflow requires a local rebase plus
  `--force-with-lease` instead.

Supply chain:

- All 91 GitHub Actions references in this repository are pinned to 40-character
  commit SHAs; zero floating tags.
- "All dependencies pinned by hash" would be false: npm, pip and container
  image layers are not all pinned, which is why Scorecard's
  Pinned-Dependencies score is 8/10. This is an open gap.

## 3. CBOM

- Generated as CycloneDX 1.6, currently 9 cryptographic components (AES,
  ML-DSA, ML-KEM, P-256/ECDH, SHA-256, SLH-DSA, SM2, SM3, SM4). Project-specific
  facts live under the `fibemate:` namespace rather than being forced into
  standard fields.
- Generation is deterministic (`SOURCE_DATE_EPOCH`, fixed serialNumber). The
  release pipeline runs a drift check (`node scripts/build-cbom.js --check`) and
  an official-schema validation (`tools/validate-cbom.cjs`; the `bom-1.6`,
  `spdx` and `jsf` schemas are vendored in the repository).
- The `bom-check` job that gates pull requests covers BOM, encoding corruption
  and experimental-code isolation. **CBOM schema validation is not a pull
  request gate yet.** That is a gap, not a completed item.

## 4. Formalization

The formalization lives in a separate public repository, `vwz-formalization`
(GPL-3.0), in Isabelle/HOL, session `VWZ_A3_Aligned`. It is separate because the
toolchain, release cadence and repository size all differ from the product code.

Ledger, generated by a script rather than typed by hand: 56 lemmas, **12**
`sorry`. By tier: T0 17/0, T1-A 16/0, T1-D 5/2, T2 10/6, T3 8/4.

What has a body:

- A field representation for `F_3329`.
- A fuel-parameterized Gauss-Jordan reduction, so `mat_rank`, `dim_nullspace`
  and `mat_inv` are no longer uninterpreted. Fuel makes the recursion
  structural and removes the termination proof. Correctness is *not* claimed:
  that the reduction reaches a normal form, that rank equals the field rank, or
  that the inverse is two-sided are all left open.
- The Section 3.1 LCG as a state machine (`nat => nat * nat`). The rejection
  sampler is proved partially correct: if it returns, the result has the right
  length, the points are pairwise distinct, and they lie in range. Termination
  holds with probability 1, and this session has no measure theory, so nothing
  stronger is asserted.
- The Section 3.3 row-addition matrix generator, the four matrices drawn in the
  order the spec fixes, and `KeyGen` as a definition that fills the Section 3.6
  fields.

What is explicitly open:

- `T2_B3` (the four generated matrices are invertible) is still `sorry` and is
  tagged `TODO(proof)`. The statement is true -- only row additions are used, so
  the determinant is 1 -- but the bridge is missing: associativity of
  `mat_mult`, or invariance of invertibility under a row addition. No assumption
  is used to paper over it.
- `T2_B7` (every slice of psi has rank 2) was **refuted by machine**: a
  counterexample satisfies the premises and has rank 0. It is recorded in
  `VWZ_Refutations.thy`. The defect is in the statement, not in a proof attempt,
  and the refutation is kept in the repository rather than deleted.
- `hash_target`, `rows3_of`, `Eval`, `Sign`, `Verify`, `sample_below`,
  `nullspace`, `solve_linear` and `mat_solve` remain uninterpreted, each tagged
  `TODO(define)` with the missing spec content. No placeholder that silently
  ignores its arguments was written: that would turn the surrounding lemmas into
  statements about an invented matrix, which is worse than an honest hole.
- The repository has no CI and no separate CONTRIBUTING file yet. Build and
  counting commands are in the README. Build with
  `isabelle build -D aligned`; `isabelle build -D neg` is a negative control and
  must fail, because it contains a deliberately false statement.

## 5. Open gaps, ordered by effort

1. Matrix algebra: associativity of `mat_mult` for rectangular matrices,
   "left-multiplying by an elementary matrix equals one row addition", and the
   inverse of an elementary matrix. Together these close `T2_B3`.
2. The remaining four T3 obligations: probability and the security layer, which
   need `hash_target` and friends defined first.
3. ACVP vectors through the public API: `fml-dsa` forwards the FIPS 204
   `context` and `extraEntropy` options and has a behavioural check (verification
   passes with the context and fails without it), but the 75/75 KAT covers
   KeyGen only. Vector-level `sigGen` / `sigVer` coverage is missing.
4. Tests and CI in `fibemate-react-native`: the `node:test` pattern already works
   in `fibemate-mobile`, while the React Native repository's `test` script only
   runs `jest`, and whether it silently passes with no test files has not been
   measured.
5. CBOM schema validation as a pull request gate, and hash pinning for npm, pip
   and image layers.
6. Outside code review: Scorecard Code-Review 0/28. Every substantive review
   changes that number.

## 6. How we work

- Commits carry DCO signoff. When a branch falls behind the base, rebase
  locally; do not use GitHub's "Update branch" button.
- Errors are acceptable; concealing them is not. A pull request that overturns an
  existing conclusion with evidence gets priority, and the overturned statement
  stays in the repository (`T2_B7` is the example).
- Claims must match implementations. If the code does not have the object, the
  document says `TODO(define)` rather than inventing semantics.
- Before submitting, show your evidence: the command, its output, and where
  relevant a byte-level check (encoding, BOM).

## 8. Who this is not for

- Teams that need a production-ready cryptography library with an SLA. This is
  not one.
- Readers who want star counts and are uncomfortable with "unfinished proofs
  must be labelled as unfinished".
- Anyone expecting "generated by AI, therefore merged". The gates reject it and
  so does review.

If you can fill any of the gaps above, open an issue or a pull request.
